# SQL + Python ETL pipeline for business reporting

A small but complete batch ETL pipeline: messy customer, product and
order extracts go in; clean, conformed core tables and reporting-ready
SQL marts come out, with data-quality checks, a quarantine for bad rows,
retries for late-arriving records, idempotent re-runs and a CLI. It runs
on a laptop with Python and DuckDB, and the SQL is written so it ports
to SQL Server, Postgres or a Fabric / Synapse warehouse.

A client-facing demo for data-engineering / analytics-engineering work
and a piece of evidence toward a QQI Level 9 (Master's) RPL file.

**Data status:** **SYNTHETIC** extracts for a fictional Irish online
retailer, generated by [`src/generate_sources.py`](src/generate_sources.py).
Every defect is injected on purpose and logged, so the pipeline can be
scored against a known answer. See [`data/README.md`](data/README.md).

New to the code? Start with the [code walkthrough](CODE_WALKTHROUGH.md).
For a non-technical summary, read the [case study](CASE_STUDY.md).

## Problem

Most small and mid-sized businesses report from CSV exports of their
shop, CRM and finance systems, glued together in Excel. Every month
someone fixes the same problems by hand: duplicate rows from re-exports,
dates in three formats, prices typed as `€12,50`, orders for customers
who are "not in the system yet", and sterling orders mixed with euro.
The numbers drift and nobody trusts them.

The brief: an automated pipeline that

1. cleans and standardises the extracts with **rules that are tested**;
2. **never silently drops** a row — rejects go to a quarantine with a reason;
3. can be **re-run safely** (same input → same output, no double counting);
4. produces **marts** a BI tool can use directly (monthly revenue by
   channel, customer summary, product performance);
5. **reconciles** to an independent expected total, and stops when a
   critical check fails.

## Approach

```
data/raw/<batch>/  ──extract──►  clean (pandas, pure functions)  ──►  load (DuckDB)
  manifest + hashes              standardise, dedupe, split           core.* upserts on keys
                                 clean / rejected + reason            FK checks vs loaded parents
                                                                      etl.quarantine (+ retry)
                                                                      etl.batch_log / run_stats
                                          ──►  transform (sql/*.sql)  ──►  validate (15 DQ checks)
                                               mart.fct_sales_line          error → exit 1
                                               mart.monthly_revenue         warn  → report
                                               mart.customer_summary
                                               mart.product_performance
```

- **Extract** reads everything as text, records a SHA-256 per file and
  refuses folders not tagged as synthetic demo data.
- **Clean** ([`src/etl/clean.py`](src/etl/clean.py)): day-first date
  parsing (never month-first), money parsing, country / phone / email
  normalisation, exact-duplicate removal, and a reject reason for every
  row it will not load.
- **Load** ([`src/etl/load.py`](src/etl/load.py)): dimensions first,
  then a **retry** of quarantined orphans whose parent has now arrived,
  then orders and lines with referential checks against what is in the
  warehouse. `INSERT OR REPLACE` on primary keys makes loads idempotent.
  A batch with identical file hashes is skipped unless `--force`.
- **Transform** ([`sql/`](sql/)): marts rebuilt from core on every run.
  Money is converted to EUR at the order month's rate in `DECIMAL`
  arithmetic and rounded half-up to the cent.
- **Validate** ([`src/etl/validate.py`](src/etl/validate.py)): key
  uniqueness, foreign keys, accepted values, FX coverage,
  mart-to-fact reconciliation, and warning thresholds.
- **CLI** ([`src/cli.py`](src/cli.py)): `run`, `run-all [--force]`,
  `status`, `export`, `reset`.

### Idempotency and ordering

| Scenario | Output identical to a single clean run? |
| --- | --- |
| Re-run with the same files (skipped by hash) | **yes** |
| Forced reprocess of both batches | **yes** |
| One batch per CLI call | **yes** |
| Batches loaded **newest first** | **no** — 29 of the 40 moved customers keep their old county |

Comparison uses an MD5 of every business column of the 7 core and mart
tables. Runtime for both batches: **5.0 s** on the build machine.

## How to run

From this folder, Python 3.11+ (developed on 3.13.5):

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python src/generate_sources.py     # SYNTHETIC raw extracts + ground truth
python src/cli.py reset
python src/cli.py run-all          # load both batches, build marts, run DQ checks
python src/cli.py status           # row counts and quarantine summary
python src/cli.py export           # marts -> reports/marts/*.csv
python src/evaluate.py             # reconciliation, detection, idempotency -> reports/
pytest -q                          # 18 tests (unit + integration)
```

The marts in `reports/marts/` load straight into Power BI, Excel or
Tableau.

## Client value

- **Numbers that reconcile to the cent**, with every excluded row
  listed and explained in the quarantine.
- **Safe re-runs**: run it twice by mistake and nothing doubles.
- **Late data handled automatically** instead of by a monthly manual fix.
- **Stops loudly** when something critical is wrong (e.g. a missing FX
  rate fails the run — tested).
- Plain SQL marts your BI developer can read and extend.

## Critical evaluation

Written with QQI / NFQ Level 9 expectations in mind.

- **Perfect scores on injected defects are expected, not impressive.**
  I wrote both the defects and the rules. The useful evidence is the
  *reconciliation* (format handling, FX, dedupe and retries all have to
  be right for revenue to match to the cent) and the idempotency tests.
  Real extracts will contain defects nobody anticipated; that is what
  the quarantine and warnings are for.
- **Out-of-order loading is not safe.** SCD type 1 here means "the last
  batch loaded wins", so loading the older extract after the newer one
  reverted 29 county changes. A production version should compare a
  source `updated_at` (or the extract date) before overwriting, or keep
  SCD type 2 history.
- **A generator bug taught a real lesson.** The first version split
  batches with `pd.to_datetime(format="mixed", dayfirst=True)`, which
  silently swapped day and month in ISO dates and produced 369
  "future-dated" orders instead of 12. The cleaner now tries explicit
  formats only, and a unit test pins day-first behaviour.
- **Duplicate detection is exact-match only.** Near duplicates
  (the same person with two customer IDs) need fuzzy matching and a
  human review queue; not attempted here.
- **Scale.** ~18k lines per batch takes seconds. Pandas cleaning would
  need to move into SQL or Spark at tens of millions of rows; the
  medallion version in project 14 shows that direction.
- **Retry cost.** Quarantine retries re-read every open row each run;
  fine here, but should be bounded (age-out, max attempts) in production.
